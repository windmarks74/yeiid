## 4. 우리가 약한 지점 — 7개

### 🔴 높음

**① 한국사능력검정시험(한능검) 규격이 통째로 없다**
mirifit 은 검사·가이드 양쪽에 있다(120×160px). 우리는 앱 프리셋도, 규격 페이지도 없다.
→ 검색 수요가 있는 규격 하나가 통째로 빠진 것이다. 새 유입 경로가 된다.
⚠️ 착수 전 **공식 출처 확인 필수** — `usage.ts` 의 `source.verified` 규칙을 따른다.

**② 출처가 서로 다르다는 것을 우리는 안 드러낸다**
mirifit 큐넷 가이드는 **공식 안내 3곳이 서로 다른 값을 준다**는 걸 표로 보여준다
(원서접수 안내: 언급 없음 / FAQ 1000800: 150px, 공인중개사 한정 / FAQ 1000033: 300×400).
그리고 **가장 높은 기준을 택한 이유**까지 쓴다. 인쇄 크기는 출처마다 2.5×3.5 / 3×4 /
3.5×4.5 로 갈려서 **자동 판정을 하지 않겠다고 선언**한다.

우리는 값 하나만 제시한다. mirifit 방식이 **신뢰도에서 앞서고, 그 자체가 검색 소재**다
("총정리", "공식 안내가 다른 부분"). 블로그 3·4편에서 "떠도는 숫자에 근거가 없다"를
다뤘는데, **한 발 더 나가면 "공식끼리도 다르다"** 가 된다.

**③ HEIC 를 지원하면서 아무 데도 안 쓴다**
`src/imageUtils.ts` 가 `heic2any` 로 아이폰 HEIC 를 자동 변환한다(확인함). 그런데
스토어 설명·규격 페이지·블로그 어디에도 없다. mirifit 은 **전용 변환 페이지 + 블로그 글**로
유입을 받는다. **비용 거의 0, 이미 되는 기능을 말만 하면 된다.**

### 🟡 중간

**④ 실제 오류 메시지를 쓰지 않는다**
mirifit 은 큐넷 실제 문구 **"사진 판독이 불가합니다"** 를 재현하고 원인 7가지를 붙인다.
사람들은 막혔을 때 **에러 문구 그대로 검색한다.** 우리는 "흔한 반려 사유"로 일반론만 쓴다.
→ 증상 기반 글(`/blog/photo-upload-failed/` 같은)이 우리에겐 없다.

**⑤ "출처 재확인 필요" 같은 항목 단위 신뢰 라벨이 없다**
mirifit 은 항목마다 검증 수준을 표시하고, 근거가 약하면 숨기지 않고 **명시**한다.
우리도 비슷한 걸 하지만(토익 "공식 픽셀 규정 없음", 큐넷 "200KB 는 접수 가이드 기준")
**항목 단위가 아니라 문단 단위**라 눈에 덜 띈다.

### 🟢 낮음

**⑥ 크기 비교표에 체감 기준이 없다** — mirifit 은 "스마트폰 사진 대비 비율"을 넣어
사용자가 크기를 직관적으로 이해하게 한다. 우리 `/resume` 비교표는 수치만 있다.

**⑦ 단독 유틸 페이지가 없다** — 압축·변환만 필요한 사람의 유입 경로. 다만 우리는 앱이라
웹 도구를 따로 만들 이유가 약하다. **하지 않는 쪽에 가깝다.**

앱은 6월부터 있었지만 **앱 내부 텍스트는 공개 웹이 아니라** 크롤링 대상이 아니고,
그들 제품은 앱이 아니라 웹 검사 도구다.

닮은 이유는 **수렴**으로 설명된다:

- "서버로 안 보냄"은 정적 웹사이트의 기본 구조(백엔드 0)이고 사진 도구의 흔한 소구점.
- 출처·확인일 표기는 규격 콘텐츠의 기본기. 게다가 **그쪽이 더 깊다.**

베낀 경우 보통 남는 **동일 문장·동일 오타**가 없다.

> 반대로 그쪽이 6월에 우리 앱을 보고 웹 버전을 만들었을 가능성은 **모름**. 알아도 할 수
> 있는 게 없다 — 규격 수치는 공공 정보고 웹 검사 도구는 다른 제품이다.
> **에너지는 "베꼈나"가 아니라 §4 의 빈칸에 쓴다.**
